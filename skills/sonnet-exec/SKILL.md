# sonnet-exec — Fable 规划验收 + Sonnet 5 执行 分层模式

> 2026-08-17 建立。与 opus-exec 同构，执行模型换成 Sonnet 5：
> 分工：**主会话（Fable）只做贵模型才值得做的事**——需求分析、方案设计、拆解任务、最终验收；
> **实际写代码/改文件/跑测试等执行工作全部委派给 Sonnet 5 子代理**，执行消耗计在 Sonnet 额度上。
> 机制用 Claude Code 原生 Agent 工具（`model: "sonnet"`），零外部依赖、同会话内闭环。
> 与 opus-exec 的取舍：Sonnet 更省额度、速度快，适合改动清单明确的常规执行；
> 执行难度高（复杂重构、深调试）时改用 opus-exec。

## 何时自动启用（不必等王老师喊）

- 王老师明确说"用 sonnet 执行 / sonnet 跑一下 / /sonnet-exec"
- 改动清单明确、执行难度不高的任务（按方案写代码、批量机械改动、写测试、常规 CRUD/页面）——主动建议走本模式
- **例外（不委派给 Sonnet）**：一两行的小改动（Fable 直接做）、纯咨询/分析类问题、需要连续深度判断的调试、复杂架构级重构（这类走 opus-exec 或 Fable 亲自做）

## 执行流程

### 第 1 步：Fable 做需求分析与方案设计（不外包）

- 读必要的代码（只读关键文件，别在主会话里大面积翻文件——大范围探索也可以派 Explore 子代理）
- 有真正的设计决策（多种合理方案、影响面不确定）→ 停下来问王老师
- 产出三样东西：**改动清单**（哪些文件、改什么）、**约束**（不许动什么、风格约定）、**验收标准**（怎么判断做对了：命令 + 预期结果）
- 给 Sonnet 的方案要比给 Opus 的**更具体**：关键函数签名、数据结构、边界条件直接写进清单，少留自由发挥空间

### 第 2 步：委派 Sonnet 子代理执行

用 Agent 工具，`subagent_type: "general-purpose"`（或任务匹配的专用 agent，如 executor/designer），**`model: "sonnet"`**。

Prompt 必须自包含（子代理看不到主会话上下文），模板：

```
【任务】<一句话目标>
【项目根目录】<绝对路径>
【改动清单】
1. <文件路径>：<具体改什么，含关键代码片段/函数名/签名>
2. ...
【约束】
- 只改清单内的文件，不"顺手改进"无关代码
- 遵循现有代码风格；<项目特有约定>
- <不许动的东西>
【完成后自检】
- 跑 <验证命令>，确认 <预期结果>
- 把改动摘要（每个文件改了什么）和自检结果作为最终输出返回
```

要点：
- **一次性交付完整任务**，不拆成小步骤逐轮喂（每轮往返都花 Fable token）
- 并行无依赖的子任务 → 多个 Agent 调用放同一条消息里并发
- 需要并行改文件时用 `isolation: "worktree"` 防冲突（见 worktree-isolation 规则）

### 第 3 步：Fable 验收（成本最小化地验）

- 优先跑**命令级验证**（tsc/测试/语法检查/冒烟 curl）——便宜且客观
- diff 抽查关键文件（git diff --stat 先看范围，再点开可疑的），不逐行通读全部改动
- Sonnet 执行的验收比 Opus 更严一点：重点抽查边界条件处理和是否"顺手"改了清单外的文件
- 不合格 → 把具体问题写成新的执行指令，再派一个 Sonnet 子代理修（不要 Fable 自己上手改，除非是一两行）
- 合格 → 按项目规矩收尾（文档同步、git 提交）并向王老师汇报

## 硬边界（撞到才升级）

- Sonnet 子代理连续 2 轮修不好同一个问题 → **先升级到 Opus 子代理**（opus-exec 模式）再试一轮；仍不行 Fable 亲自诊断
- 涉及业务不变量/数据安全的判断（删数据、改契约、动生产）
- 王老师明确要求 Fable 亲自做的部分

## 额度参考

- 分工得当时，主会话每轮只花"读方案+写指令+看验收结果"的少量 Fable token，
  执行的大头（读大量文件、写大量代码、反复跑测试）都在 Sonnet 侧，比 Opus 侧更省
- 三档速查：sonnet-exec（常规执行，最省）→ opus-exec（复杂执行）→ Fable 亲自（深度判断/小改动）
